## Interfaces and key decisions

- `runCheck({ text }, deps)` — `text` is the **only** request field: there is structurally no browser-supplied identifier that could become authority (NFR-M4-02/FS-M4-08). `deps.session` is an opaque server-verified context only the entitlement port interprets.
- Rejections (`invalid-input`, `access-blocked`, `quota-denied`, `rate-denied`) are terminal, carry a safe message, make zero provider calls and are never counted (X-13 §4.1: no event for input/auth/quota rejection before a check is accepted).
- Analysed results use only the three valid X-13 pairs: `completed`+`rules_and_ai`, `limited`+`rules_only`, `unavailable`+`none` (category `unknown_other`, never a "safe" outcome). Missing key or unpermitted budget → the designed labelled rules-only state (FS-M4-05); provider failure/timeout/invalid reply → unavailable (FS-M4-06); invalid output is never "repaired" into a completed result (FR-M4-04).
- Access mapping follows [the access-policy decision](../../contracts/M4-access-policy-decision.md): active/trial allow; cancelled allows strictly until expiry; suspended/past-due/expired/unverifiable block; unknown plan ids get no invented quota (the repo's current M2 `free`/`premium` shape therefore blocks until M2 reconciles with the confirmed Sentinel/Guardian/Aegis decision).
- Quotas/limits come from [the usage-quotas decision](../../contracts/M4-usage-quotas-and-funding-decision.md) §1 (2,000-char cap; 5/min burst; 60/5, 200/15, 600/40; trial 15). Trial monthly quota is **first-use anchored** (review fix #7 — 30-day periods); the 7-day window boundary is the entitlement layer's job. Exact duplicate/count policy stays OD-M4-06.
- The base provider reply schema (`verdict`, `category`, `taxonomy_version`, `reason`) remains structurally compatible. The owner-approved local presentation extension adds optional `risk_level` and `reason_highlights`, normalised into `riskLevel` (`low` / `suspicious` / `high` / `undetermined`) and `reasonHighlights` (exact UTF-16 `{ start, end, excerpt }` spans in the reason). Missing/invalid optional metadata preserves the valid base reply, uses neutral undetermined risk and omits invalid highlights. At most four input excerpts are considered; first occurrences are merged/deduplicated and combined emphasis cannot exceed 35% of the reason. No severity is attributed to local matches and no confidence is calibrated. Broader OD-M4-04 product/prompt/deadline acceptance remains open; this local display refinement changes no X-13 event contract.

## M6-04 activity-evidence builder — 18 November 2026

`activity-evidence.ts` implements the **producer half** of M6-04: a pure builder/validator for the X-13 §5.1 `m4.scam_activity_evidence` summary. It derives the mandatory limitation set from the availability state (`available`/`stale` → the three baseline IDs plus `stale_evidence` for stale; `unavailable` → a null attempt plus one of `no_retained_evidence`/`not_implemented`/`source_unavailable`), enforces the §4.1 status/mode pairs, refuses an attempt later than `as_of`, and refuses unknown, duplicate or state-contradicting limitation IDs instead of silently dropping them. `subject_ref` gets hygiene checks only (no whitespace, `@`, phone, JWT or URL shapes; ≤128 chars) — that is **not** subject binding or authorization. **No network I/O and no clock:** the caller supplies `asOf` and the attempt facts. The payload has exactly seven fields and cannot carry message text, contacts, category, verdict, reason, confidence, counts or scores. `isValidAnalysisPair` and `isRfc3339Utc` are additive exports from `x13-event.ts` so the pair table and timestamp rule exist once. Tests: `activity-evidence.test.ts` (**15/15**). Full suite after this addition: **464/464**. M6 consumer review, delivery, retention, ordering and freshness remain open.
