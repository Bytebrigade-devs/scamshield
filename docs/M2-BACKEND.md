# M2 backend connection — 7 November 2026

The saved team design uses Next.js App Router, TypeScript and Supabase Auth/PostgreSQL. The existing API is now connected to the UI. Backend mode is the default; set NEXT_PUBLIC_M2_MODE=demo to restore the interim presentation. Restart Next.js after changing this build-time public setting. There is no automatic fallback to demo data when authentication or the server fails.

## Setup

1. Copy .env.example to .env.local and provide the Supabase URL, anon key and server-only service role key. Keep the latter out of browser code and source control.
2. Review docs/m2-schema.sql with the team schema steward, then apply it to the development Supabase project. Existing legacy Free/Premium records require an agreed migration; the SQL intentionally aborts rather than converting them.
3. Enable email/password Auth and the email provider. Registration is verified with an emailed **confirmation link**; password reset uses an emailed **code** (owner decision, 21 November 2026). The code length is a Supabase project setting — this project issues 8 digits — so the UI accepts 6 to 10 and never pins one length. The **expiry window** is a project setting too (`mailer_otp_expiry`), and GoTrue applies one value to the confirmation link and the reset code alike, so `AUTH_OTP_EXPIRY_SECONDS` must match it. The app is set to 300 seconds (5 minutes); the full live check on 28 November 2026 found the project still accepting a code after 320 seconds, so the project setting is **not aligned yet**.
   - `/signup` posts to M2's `POST /api/auth/confirmation-link`, which creates the account with the service-role admin API (confirmation left off, so Supabase sends nothing) and emails Supabase's own confirmation link (`generateLink({ type: "signup" })` → `action_link`) through the configured sender. When no sender is configured the route answers 503 and the page falls back to client-side `signUp`, letting Supabase's mailer deliver the link. A login from an unconfirmed account offers "Resend confirmation email", which calls the same route with `{ resend: true, password }`. Before generating anything the route proves the credentials with `signInWithPassword`: GoTrue answers `email_not_confirmed` only for an existing account whose password is correct, while an unknown address or a wrong password gets the same content-free `200 {"ok":true}` and no mail. This gate exists because `generateLink({ type: "signup" })` **creates** an unconfirmed account for an unknown address — verified live on 28 November 2026 — so an ungated resend could open accounts for addresses the caller does not own. A resend therefore never creates an account; the screen keeps the typed password for that button even after the visible field is cleared. A failed send deletes the freshly created account, so no unusable unverified row is left behind.
   - `/forgot-password` posts to M2's `POST /api/auth/recovery-code` first (Resend, or the development outbox); when that answers 503 it falls back to Supabase's `resetPasswordForEmail`. The code is generated with the service-role admin API (`generateLink({ type: "recovery" })` → `email_otp`), so it does not depend on the Supabase project's SMTP settings. The code step then calls `verifyOtp({ type: "recovery" })`, and the session that returns is what lets `/reset-password` set the new password. That screen still accepts a `PASSWORD_RECOVERY` link session, so a link-based recovery email keeps working too.
   - `node scripts/check-resend.cjs [address]` verifies the sender without printing the key: it lists the verified domains, then optionally sends one test mail.
   - `node scripts/check-otp-expiry.cjs [--quick]` proves the live window: it creates throwaway accounts, verifies a fresh code, then (without `--quick`) waits the window out and asserts the same call is refused. It prints no codes, tokens or links, and it is the check that tells you `AUTH_OTP_EXPIRY_SECONDS` and the project setting agree.
   - To make Supabase's recovery mail carry the code instead of a link, replace the **Reset password** template body with: `<h2>Reset your password</h2><p>Your ScamShield password reset code is:</p><p style="font-size:32px;letter-spacing:4px;font-weight:bold;">{{ .Token }}</p><p>Enter it on the reset page. It can be used once and expires soon. If you did not request this, ignore this email - your password stays unchanged.</p>`
   **Both flows are sent by M2 through Resend**, so delivery is one configuration rather than two:
   - *Needs* `RESEND_API_KEY` plus `AUTH_EMAIL_FROM` (falling back to `TRIAL_EMAIL_FROM`) on a domain verified with Resend. Create the key with **Sending access**, restricted to that domain — this app only calls `POST /emails`, so Full access would be an unnecessary grant. Without a key and a sender each route answers 503 "Email delivery is not configured on this server", and the screen shows that verbatim instead of claiming a message was sent.
   - *Supabase's own mailer is no longer the primary path*, so Authentication → SMTP Settings and the Confirm sign up / Reset password templates are not used by these two flows. They remain an emergency fallback: `/signup` falls back to client-side `signUp`, and `/forgot-password` falls back to `resetPasswordForEmail`, when the M2 route answers 503. Those fallback mails *are* constrained by the project's SMTP configuration and rate limits, which is why the templates in `scamshield-m2-private/docs/email-templates/` are still worth keeping current.
   Reset-code safety: the code is never returned to the browser and never logged; an unknown address gets the same `200 {"ok":true}` as a known one; and each address and caller is limited to 3 requests per 10 minutes by an in-memory limiter that a server restart clears. The confirmation route allows 5 per address over the same window, because a five-minute link gets re-requested more and it only activates an account whose password the caller already set.
   Delivery failures are reported as themselves: a Resend 429 becomes a 429 "the email service is busy, wait about a minute" rather than a 502 "try again", and the status plus Resend's own reason go to the server log — never the key, the code, or the link. A 401/403/422 still fails closed with a 502.
   Local development without a mail sender: set `AUTH_MAIL_DRIVER=outbox` (optionally `AUTH_MAIL_OUTBOX`, default `.dev-outbox`, gitignored). The message is then written to that folder and printed in the server terminal instead of being emailed, and the response carries `devChannel: "outbox"` so the screen states plainly that nothing was emailed. A production build refuses this driver and returns 503 — a reset code is never written to disk in production. Resend takes precedence whenever a key and sender are present, so remove the driver once a key is configured: a missing key should then fail loudly instead of quietly writing codes to disk.
   Resend prerequisites, per its own documentation: a **verified domain** (SPF + DKIM, ideally DMARC on the sending subdomain) and a key created with Sending access. Before verification, `onboarding@resend.dev` can only deliver to the Resend account owner's own address. A Gmail address cannot be the sender at all — Resend answers 403 "The gmail.com domain is not verified" for `from: someone@gmail.com`, with or without a display name — but it can be the Reply-To: set `AUTH_EMAIL_REPLY_TO` to a monitored inbox (Gmail or otherwise) and every auth email carries that header, which is what was verified on 23 November 2026. The free tier allows 100 emails per day within 3,000 per month — enough to rehearse, not to load test. Keep the Site URL and the `/account/subscription` and `/reset-password` redirect URLs allowlisted, because the confirmation link uses them. In demo mode nothing is sent and the reset screen shows the fixed code `000000`.
   Expiry: nothing in this app can enforce it. GoTrue owns the token, and `/auth/v1/verify` answers to the anon key, so a project setting is the only real gate — `mailer_otp_expiry`, intended to be 300 seconds. `AUTH_OTP_EXPIRY_SECONDS` (default 300) is the same number on the app side, used for the email copy, the screen text and the code screen's countdown, so the three cannot drift apart. It is clamped to 60–86400, and `node scripts/check-otp-expiry.cjs` measures the live window and exits non-zero when the two disagree. As of 28 November 2026 it exits 1: the same code still verified after 320 seconds, so the project's window is longer than the app states (Supabase's default is 3600 seconds) and the project setting must be corrected. Reaching zero on screen only warns and offers a new code: the countdown is a courtesy, and a still-valid code must keep working if the copy is ever wrong. Note that Supabase has one window for every email token, so shortening it also shortens email-change and invite links.
   To send trial-start confirmations, optionally configure `RESEND_API_KEY` and `TRIAL_EMAIL_FROM` with a verified sender domain. If these are missing or delivery fails, the trial still starts and the account page reports that no confirmation email was sent.
4. Run pnpm dev. Sign up, confirm email, log in, start a trial, inspect subscription, cancel, and test recovery email/password replacement.
5. Verify two accounts cannot read each other's subscriptions and direct browser database writes are denied. Verified against the development project on 28 November 2026: two confirmed accounts each read only their own row, a direct update/insert/delete from the browser client answered `42501 permission denied for table subscriptions`, `GET /api/subscription` returned each account's own plan and a valid entitlement, and the same call without a token answered 401.

## API

All requests use Authorization: Bearer <Supabase access token>. The server verifies identity using auth.getUser(token), reads only that user's row, and derives trial and paid expiry on the server. The browser never supplies authoritative identity, access status or expiry.

| Method and endpoint | Behavior |
| --- | --- |
| GET /api/subscription | Own subscription and authoritative entitlement decision |
| PUT /api/subscription | One trial, seven days anchored at signup |
| POST /api/subscription | Mock purchase: plan, billingCycle, scenario; optional paymentMethod/promoCode |
| DELETE /api/subscription | Cancel while preserving access until expiry |

The server role performs writes; authenticated clients can only read their own subscription through RLS. Errors fail closed. Responses are not cached. A valid paid entitlement cannot currently change plan; the UI hides that demo-only action in backend mode. Cancelled plans expire at the same timestamp; there is no automatic renewal.

When a trial is allocated, the backend sends a transactional email to the verified account email through Resend, if configured. It includes the expiry in Sri Lanka time and the 15-total / 5-per-day check allowance. This message is informational; M4 still owns atomic usage enforcement.

## Payment and usage boundaries

Payments remain simulated by project requirement. A successful test checkout grants a persisted mock entitlement. This is a development/demo backend, not verified commercial billing. No live gateway or webhook is present. Checkout collects no card details at all: there is no number, expiry or security-code field, and the request carries only the plan, billing cycle, scenario and an optional promo code. Saved-card UI, DEMO10 discount, demo reset controls and invented usage counters are disabled in backend mode. Backend promo codes are unavailable.

M4 must enforce usage limits atomically and call the server entitlement helper for each protected action. M2 exposes plan limits but has no usage ledger; billing is unrelated to the safety score. No shared schema or remote database was changed during this connection work.

## Validation

Run pnpm test:subscription, pnpm test:recovery, pnpm test:m2, pnpm typecheck, and pnpm build. Local tests use mocked Supabase responses; they do not establish live database permissions, email delivery or payment processing. Two checks are deliberately outside CI because they need a live project: `pnpm check:resend [address]` (sender configuration) and `pnpm verify:otp-expiry` (the real expiry window, which takes longer than the window itself).

Auth integration follows the Supabase API: https://supabase.com/docs/reference/javascript/auth-getuser and https://supabase.com/docs/guides/auth/passwords.

Live checks against the configured development project on 28 November 2026:

- `generateLink({ type: "signup" })` returned a link **and created** an unconfirmed user for an address that did not exist; the password supplied to that call then reached `email_not_confirmed` on sign-in. The same call succeeded twice for an existing unconfirmed user. This is why resend now probes credentials first.
- A wrong password on an unconfirmed account answered `invalid_credentials`, while the correct password answered `email_not_confirmed` — the distinction the resend gate relies on.
- `check-otp-expiry.cjs --quick` verified a freshly issued recovery code (HTTP 200, session issued). The full run then exposed a mismatch: a code issued 320 s earlier still verified, so the project's email OTP window is longer than the 300 s the app states and the script exited 1. Set `mailer_otp_expiry` to 300 (or correct `AUTH_OTP_EXPIRY_SECONDS`) before trusting the copy or the countdown. The failed run also showed that the script's `process.exit(1)` skipped its `finally` cleanup; it now sets `process.exitCode` and returns, so both throwaway accounts are deleted on failure too.
- `check-resend.cjs` accepted the API key but reported **0 verified domains**. With `AUTH_EMAIL_FROM=onboarding@resend.dev`, delivery only works to the Resend account owner; for any other recipient Resend answers 403, the signup route returns 502 and does **not** fall back to Supabase's mailer (that fallback happens only on a 503 "not configured"). Verify a sending domain before relying on this path. The fixed route was also exercised end to end on a production build: unknown-address resend created nothing, a correct-password resend reached Resend and failed 403 as expected (account left unconfirmed), a wrong password sent nothing, and a signup whose mail failed deleted its account.
- Two-account isolation and RLS were verified against the development project: each account's direct `select` returned exactly its own subscription row, direct `insert`/`update`/`delete` were refused with `42501 permission denied for table subscriptions`, and `GET /api/subscription` returned the correct plan and entitlement for each bearer token (401 without one). Both throwaway accounts were deleted afterwards.
